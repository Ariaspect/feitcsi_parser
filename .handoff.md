## Hard-won findings — do not rediscover these
1. **Board wake sequence is THREE steps, not one.** `ka 01 01` (LG RS-232C power-on) → wait for boot → send `s` to enter shell mode (the console does NOT come up in a shell) → re-apply `ip addr add 192.168.50.80/24 dev eth0`. Skipping the last step leaves the board pingable-looking but ssh-dead. Implemented in `wake_board()`.
2. **luna-send output is lost when stdout is a pipe.** `ssh board "luna-send ..."` returns EMPTY while the call itself succeeds. It works with `ssh -tt` (pseudo-TTY) or by redirecting to a file on the board and cat-ing it back. Separately, luna-send returns rc=0 BEFORE the response is written, so even the file approach races; `-w <ms>` does NOT fix it. Measured on an idle associated board: luna getstatus 0-for-5, `iw`/`ip` 5-for-5.
   → Therefore: wifi association is detected with `iw dev wlan0 link` + `ip -4 addr show wlan0`. luna-send is used ONLY to fire the reconnect, and the result is judged by polling the link.
3. **This system's `date` is uutils coreutils 0.8.0, not GNU.** It silently ignores `%3N` and emits all 9 nanosecond digits. `webcam_capture.sh` takes one `date` call and slices it.
4. **CSI must be transferred over the WIRED path.** `REQUIRE_WIRED=1`, `WIRED_IFACE=enp1s0`. Exporting over the measured wifi link feeds TCP ACKs back as fresh stimulus — a feedback loop that ends with most CSI self-generated.
5. **Group id wraps at 65536 groups** ≈ 59 min at the measured 18.5 groups/s. No capture mode may reach an hour.
6. **The board's clock is offset ~14h29m from the host.** Board-emitted log lines (`05:44:32 board: ...`) are board-local, not host time. Matters for any CSI↔webcam time alignment work.
7. **There are two cameras.** `/dev/video0` is the laptop lid cam, `/dev/video2` is the USB camera (in use). `video1`/`video3` are metadata nodes, not capture devices. Use video2 — the lid cam's field of view changes whenever the laptop is touched.

## Scripts (all untracked in git)
- **`capture_mtk_hourly.sh`** — the main script. Flags: `--mode hourly|10min`, `--duration SECS`, `--show-cron`, `--help`. Precedence: `--duration` > `DURATION=` env > mode default. Modes pair a duration with its cron schedule deliberately so they cannot drift apart (a duration >= its interval would make flock skip every second run). hourly=3300s @ `0 * * * *`, 10min=570s @ `*/10 * * * *`.
  Flow: preflight (transport check → ping/serial-wake → ssh retry → wifi guard) → deploy board script by checksum → start webcam grabber → stream CSI over ssh → wait grabber → validate with MTKIndex → tar+zstd frames → scp both to lg.
- **`webcam_capture.sh`** — `./webcam_capture.sh SECONDS OUTDIR`. 1 fps from /dev/video2, MJPG native (no ffmpeg needed; ffmpeg/cv2/fswebcam are NOT installed). Uses absolute deadline scheduling, not `sleep 1`, because a grab costs ~0.6s and flat sleeps would drift. Drops first 4 frames so the sensor settles. Verified: spacing within ~20ms of 1.000s, ~78KB/frame at 640x480.
- **`capture_continuous.sh`** + `~/.config/systemd/user/csi-capture.service` — a back-to-back supervisor written earlier. NOT currently in use (cron is used instead). Still functional; it passes `DURATION=` env with no flags, which the precedence chain handles.
